% ABSTRACT
% =========================================================================
\begin{abstract}
Running a relational database on intermittently connected edge networks requires balancing local write availability against global consistency. While centralized databases rely on wide-area connectivity, and decentralized key-value stores lack cross-record relational constraints, we implemented Agentic Mesh to bridge this gap. Agentic Mesh is a masterless, zero-cloud peer-to-peer relational database designed for local environments. The architecture embeds an independent SQLite database within each peer and replicates transactions over a libp2p GossipSub mesh. We rely on an append-only ledger and vector-clock metadata for causal tracking, duplicate detection, and partition catch-up.

To integrate conversational AI without blocking the synchronous write path, the system employs a bifurcated execution model. Standard structured mutations execute immediately through a deterministic schema validator. Natural-language prompts are routed to a decoupled local language model (Gemma) that plans intent. Crucially, the model does not generate arbitrary SQL; instead, it outputs bounded relational tool operations (\texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}) that must pass the same deterministic validation layer before local commitment. While our current implementation successfully preserves local relational constraints and demonstrates convergence under validated causal replay, we note that concurrent conflicting writes can still cause replica divergence. This paper outlines the architecture, formalizes our convergence properties, and details the evaluation methodology planned for future quantitative benchmarking.
\end{abstract}

% I. INTRODUCTION

\section{Introduction}
\label{sec:introduction}

\IEEEPARstart{K}{eeping} a relational database available during a local network partition creates a problem that does not appear in a centralized deployment: each peer must be able to accept a write, but cannot immediately know whether the same key has been modified elsewhere~\cite{sarin1985partition}. While cloud-hosted engines handle this by forcing transactions through a single primary coordinator~\cite{brewer2012cap}, edge environments---like tactical networks or industrial sites---often lack reliable wide-area uplinks. Nodes in these networks need autonomous write capability backed by robust relational storage, and they must gracefully synchronize when their local network reconnects.

Building a masterless relational database to solve this exposes three practical engineering problems:

\begin{enumerate}
    \item \textbf{Decentralized Relational Invariants:} In a key-value store, peers can merge disconnected updates trivially because keys are independent. Relational databases, however, enforce foreign keys, uniqueness, and domain checks~\cite{codd1970relational, codd1974recent}. Enforcing these cross-table invariants without a central lock manager is difficult if we also want to maintain write availability during a network split.
    \item \textbf{Inference Latency on Transaction Paths:} We want to allow edge operators to query and update the database using conversational interfaces powered by local language models (like Google Gemma~\cite{team2024gemma}). However, LLM token generation is slow. If model inference sits on the synchronous write path, database throughput collapses.
    \item \textbf{Generative SQL Hallucination:} Generating raw SQL directly from user prompts is risky. End-to-end Text-to-SQL models frequently hallucinate non-existent columns, drop join predicates, or issue destructive commands~\cite{visperas2023texttosql, singh2025llmtexttosql}. Any production database needs deterministic validation before data touches the disk.
\end{enumerate}

We built \textbf{Agentic Mesh} to solve these issues for local-area networks. Instead of relying on a primary node, every peer in Agentic Mesh runs an identical software stack. We paired embedded SQLite storage~\cite{hipp2020sqlite} with libp2p GossipSub transport~\cite{trautwein2022libp2p, vyzovitis2020gossipsub} and implemented causal tracking via vector clocks~\cite{fidge1988timestamps, lamport1978time} to create a zero-cloud peer-to-peer relational mesh.

To prevent the AI components from bottlenecking the system, we implemented a \textbf{bifurcated execution pipeline}. Standard application transactions follow a high-speed, deterministic fast path directly to SQLite. Natural-language requests diverge to a local LLM planner. To solve the hallucination problem, the planner cannot execute raw SQL strings. It must map the user's intent into bounded JSON tool operations, which are then routed back through the exact same deterministic validation logic used by the fast path before any disk commit occurs.

\subsection{Research Contributions}
Our prototype demonstrates the following architectural contributions:
\begin{enumerate}
    \item \textbf{Coordinator-Free Relational Architecture:} A masterless integration of embedded SQLite, libp2p gossip dissemination, and vector-clock metadata over an append-only local replication log.
    \item \textbf{Bifurcated Execution Pipeline:} An operational split that isolates the latency of edge-LLM intent planning from the high-throughput deterministic write path.
    \item \textbf{Bounded Tool-Level Relational Abstraction:} A defensive design that forces the LLM to output structured relational operations ($\mathcal{M}_{\text{tool}}$) mapped to parameterized SQL, thereby reducing the SQL-injection attack surface.
    \item \textbf{Validated Replay Convergence Model:} A formal analysis of how multi-peer state converges under causal log replay, including a concrete examination of divergence caused by concurrent conflicting writes.
\end{enumerate}

We emphasize that Agentic Mesh's novelty lies in how these systems are integrated and structurally isolated at the edge, rather than in the individual components (SQLite, libp2p, GossipSub), which are established primitives.

\section{Background and Related Work}
\label{sec:related_work}

\subsection{Distributed and Partition-Tolerant Databases}
Managing databases over uncoordinated networks requires addressing partition tolerance~\cite{brewer2012cap}. Early designs maintained local availability by accepting writes locally and exchanging reconciliation logs when connections were restored~\cite{sarin1985partition}. Modern systems optimize this by tuning refresh delays in cluster environments~\cite{coulon2005consistency} or employing distributed multiversion concurrency control (DMVCC) to reduce coordination overhead~\cite{shao2016dmvcc}. These solutions assume high-speed datacenter interconnects. Agentic Mesh differs because it targets ad-hoc LAN environments where peers routinely suffer prolonged disconnections.

\subsection{Peer-to-Peer and Local-First Storage}
Most peer-to-peer storage mechanisms rely on Distributed Hash Tables (DHTs)~\cite{dougherty2008dht} or DAGs to synchronize data. While document-based synchronization works well for independent objects, it lacks the machinery to handle relational algebra, foreign-key cascades, or domain constraints essential for structured data~\cite{codd1970relational, codd1974recent}. We built Agentic Mesh to bring P2P replication overlays directly to embedded relational engines like SQLite, closing the gap between offline-first availability and relational integrity.

\subsection{Replication and Consistency Paradigms}
Database replication fundamentally depends on how and when updates propagate~\cite{pedone2000replication}. A masterless, update-everywhere model with lazy gossip dissemination allows our nodes to accept local writes instantly. We trade global linearizable consistency for immediate local availability, an acceptable compromise when network partitioning is the norm~\cite{vogels2009eventually}.

\subsection{CRDTs and Causal Metadata}
Conflict-Free Replicated Data Types (CRDTs) achieve eventual consistency by guaranteeing that concurrent operations mathematically commute~\cite{shapiro2011conflict}. However, translating complex multi-table referential constraints into standard CRDT primitives is not natively supported by SQLite. Instead of attempting a full CRDT implementation, Agentic Mesh uses vector clocks~\cite{fidge1988timestamps, mattern1989virtual} based on Lamport clocks~\cite{lamport1978time} purely for causal tracking. We record $V_A \parallel V_B$ relationships within our replication ledger to identify concurrent events, relying on deterministic validation rather than an unconstrained CRDT merge algebra.

\subsection{Gossip Dissemination and P2P Overlays}
Decentralized log consistency is efficiently handled by gossip protocols, which scale logarithmically without central servers~\cite{chuat2015gossip}. For transport, we implemented the libp2p stack~\cite{trautwein2022libp2p} due to its built-in stream multiplexing and encrypted Noise handshakes. We specifically use GossipSub~\cite{vyzovitis2020gossipsub} because it natively suppresses redundant message rebroadcasts, which prevents flooded networks when peers reconnect and exchange backlogged transactions.

\subsection{Natural-Language Database Interfaces and Tool Use}
As natural language database interfaces transitioned to LLMs, research revealed significant accuracy drop-offs on multi-table schemas~\cite{visperas2023texttosql}. Generating raw Text-to-SQL introduces severe execution risks, including schema hallucination and destructive commands~\cite{singh2025llmtexttosql}. Bounding LLMs to distinct tools significantly improves execution safety~\cite{schick2023toolformer}. In Agentic Mesh, we apply this by restricting our local LLM to a planner role. It can only emit JSON-formatted tool operations, enforcing a strict boundary between probabilistic generation and deterministic execution.

\section{System Model and Problem Statement}
\label{sec:problem}

\subsection{System and Network Model}
Our environment consists of $K$ independent edge nodes $\mathcal{N} = \{n_1, n_2, \dots, n_K\}$ operating on an ad-hoc local area network. The system design relies on the following operational boundaries:
\begin{itemize}
    \item \textbf{Topology:} The mesh is entirely coordinator-free. There is no leader election, no primary replica, and no cloud sequencer.
    \item \textbf{Network Assumptions:} We rely on asynchronous TCP message-passing. Because edge networks are inherently unstable, nodes must tolerate packet loss, high latency, and extended network splits. Peers find each other on the LAN via multicast DNS (mDNS).
    \item \textbf{Storage Model:} Every node writes to its own local SQLite database file, strictly operating in Write-Ahead Logging (WAL) mode for concurrency and durability.
    \item \textbf{Failure Model:} We assume a crash-recovery model where nodes can abruptly disconnect or reboot. SQLite's WAL ensures data files remain uncorrupted. We assume nodes are honest-but-fallible; preventing Byzantine actors is outside our current scope.
\end{itemize}

\subsection{Formal Requirements}
We engineered the system to meet six specific operational criteria:
\begin{itemize}
    \item \textbf{R1 (Masterless Availability):} A peer must be able to read and write to its local database immediately, even if the network interface is physically disconnected.
    \item \textbf{R2 (Local Relational Invariant Preservation):} A transaction cannot be committed unless it satisfies all schema constraints, including foreign keys, uniqueness, and custom domain rules.
    \item \textbf{R3 (Causal Log Synchronization):} Gossip dissemination must include vector-clock metadata and unique transaction IDs so peers can detect duplicates and accurately catch up after a partition.
    \item \textbf{R4 (Deterministic Validation Guardrails):} Direct API calls, incoming gossip transactions, and LLM-generated operations must all be verified by the exact same deterministic schema validator.
    \item \textbf{R5 (Latency-Isolated AI Planning):} The heavy computational cost of parsing natural-language prompts must never block the execution of standard structured transactions.
    \item \textbf{R6 (Zero-Cloud Operation):} From database writes to LLM inference, the entire stack must run on the local hardware.
\end{itemize}

\subsection{Relational Persistence Layer}
For local storage, we embedded SQLite into our Node.js runtime using \texttt{better-sqlite3}. When a peer starts up, it enforces three critical PRAGMA configurations:
\begin{lstlisting}[language=SQL]
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = NORMAL;
\end{lstlisting}
Using WAL mode is necessary because it allows us to handle incoming read queries concurrently with a busy writer thread processing incoming gossip. We relax the synchronization guarantee to \texttt{NORMAL} because lazy checkpoint fsyncing reduces wear on edge flash memory while retaining reasonable crash resilience.

The baseline database schema is shown in Listing~\ref{lst:schema_ddl}. We normalized the core tables into Third Normal Form (3NF) to prevent update anomalies across \texttt{categories}, \texttt{items}, and \texttt{suppliers}. We record every successful local mutation in an append-only table named \texttt{\_mesh\_log}, which serves as the authoritative replication ledger for the peer.

  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  description TEXT
);

  id INTEGER PRIMARY KEY AUTOINCREMENT,

\subsection{Networking and Gossip Overlay}
We wired the peers together over TCP using libp2p. The networking layer consists of:
\begin{itemize}
    \item \textbf{Transport \& Encryption:} Raw TCP sockets encrypted and authenticated locally via the Noise protocol (\texttt{libp2p-noise}).
    \item \textbf{Stream Multiplexing:} The Mplex library to multiplex multiple virtual streams over a single connection.
    \item \textbf{Discovery:} Multicast DNS (\texttt{libp2p-mdns}), which allows peers joining the LAN to automatically broadcast their presence without manual IP configuration.
    \item \textbf{PubSub Engine:} A GossipSub mesh that handles message propagation across two dedicated topics: \texttt{mesh:transactions} for live writes and \texttt{mesh:sync} for partition recovery.
\end{itemize}

Because gossip meshes naturally echo messages, we implemented an LRU message cache with a capacity of 1000 UUIDs to drop redundant transaction broadcasts before they reach the validator.

As shown in Fig.~\ref{fig:dual_pipeline}, the core of our latency isolation strategy is the bifurcated execution pipeline. We split traffic based on the shape of the request.

\subsection{Deterministic Fast Path}
If a request arrives as a structured JSON object containing a target table and data payload, our router skips the LLM entirely. The payload falls immediately into the deterministic schema validator, which performs five strict invariant checks against the local database:
\begin{enumerate}
    \item \textbf{Attribute Completeness:} Rejects the payload if it is missing any non-nullable schema attributes.
    \item \textbf{Type Conformance:} Enforces primitive datatype matching (e.g., ensuring \texttt{price} $\in \mathbb{R}$ and not a string).
    \item \textbf{Domain Bounds:} Checks payload values against SQLite \texttt{CHECK} constraints (e.g., \texttt{price} $> 0$).
    \item \textbf{Referential Existence:} Queries local indexes to ensure locally referenced foreign keys actually exist before allowing the write.
    \item \textbf{Uniqueness Pre-check:} Scans for conflicting unique keys (like an identical \texttt{sku}), safely ignoring self-rows during updates.
\end{enumerate}

Algorithm~\ref{alg:fast_path} outlines the exact logic we use to validate, commit, and broadcast these fast-path operations.

\begin{algorithm}[t]
\caption{Deterministic Fast-Path Commit and Propagation}
\label{alg:fast_path}
\begin{algorithmic}[1]
\Require Mutation $\mathcal{O} = \langle \text{op}, \text{table}, \text{data} \rangle$, Peer ID $n_i$, Local DB $\mathcal{D}_i$, Clock $V_i$
\Ensure Success flag $b \in \{\text{TRUE}, \text{FALSE}\}$, Transaction ID $\tau_{\text{id}}$
\State $\mathcal{V} \gets \text{ValidateSchema}(\mathcal{O}.\text{op}, \mathcal{O}.\text{table}, \mathcal{O}.\text{data}, \mathcal{D}_i)$
\If{$\mathcal{V}.\text{valid} = \text{FALSE}$}
    \State \Return $\langle \text{FALSE}, \emptyset \rangle$
\EndIf
\State $\tau_{\text{id}} \gets \text{UUIDv4}()$
\State $V_i[n_i] \gets V_i[n_i] + 1$
\State \textbf{begin transaction}
\State Execute parameterized SQL for $\mathcal{O}$ on $\mathcal{D}_i$
\State INSERT into \texttt{\_mesh\_log} values $(\tau_{\text{id}}, \mathcal{O}.\text{op}, \mathcal{O}.\text{table}, \text{JSON}(\mathcal{O}.\text{data}), \text{JSON}(V_i), n_i)$
\State \textbf{commit transaction}
\State $\mathcal{E} \gets \langle \tau_{\text{id}}, \text{TRANSACTION}, n_i, \text{Timestamp}(), V_i, \mathcal{O} \rangle$
\State $\text{GossipSub.publish}(\text{``mesh:transactions''}, \text{Encode}(\mathcal{E}))$
\State \Return $\langle \text{TRUE}, \tau_{\text{id}} \rangle$
\end{algorithmic}
\end{algorithm}

\subsection{Decoupled AI Planning Path}
When a user sends an unstructured natural-language prompt (like \textit{``Add 15 ergonomic mechanical keyboards under Electronics priced at \$120 each''}), the router forwards it to our AI Planner.

We inject the current SQLite schema and a lightweight JSON snapshot of existing category IDs and suppliers directly into the system prompt. We then query a local Gemma 4 E2B model running through Ollama. Rather than risking raw SQL generation, we force the LLM to output a bounded set of relational operations:

\begin{equation}
\mathcal{M}_{\text{tool}} = \left\{
\begin{aligned}
&\text{INSERT}(\text{table}, \text{data}), \\
&\text{UPDATE}(\text{table}, \text{data}), \\
&\text{DELETE}(\text{table}, \text{data})
\end{aligned}
\right\}
\end{equation}

Once the executor receives this JSON array, it feeds each operation back into the deterministic fast path. This is our primary defense mechanism: if the LLM invents a non-existent category ID or tries to insert a duplicate SKU, the deterministic validator catches it and aborts the operation. Because the LLM sits off the critical path, the deterministic fast path remains available even if the Ollama service crashes; the node simply logs a warning and continues executing incoming fast-path gossip.

\section{Causal Replication and Conflict Handling}
\label{sec:replication}

\subsection{Causal Vector Clock Formalism}
We use vector clocks to track the causal history of transactions across the mesh.

\begin{definition}[Vector Clock]
Each peer $n_i \in \mathcal{N}$ maintains a vector clock $V_i: \mathcal{N} \to \mathbb{N}_0$, where $V_i(n_j)$ denotes the number of logical mutations originated by peer $n_j$ that have been causally applied at peer $n_i$.
\end{definition}

\begin{definition}[Causal Precedence and Concurrency]
For any two transaction vector clocks $V_A$ and $V_B$:
\begin{align}
V_A \le V_B &\iff \forall k \in \mathcal{N}, \; V_A(k) \le V_B(k) \\
V_A < V_B &\iff (V_A \le V_B) \land (\exists k \in \mathcal{N}, \; V_A(k) < V_B(k)) \\
V_A \parallel V_B &\iff \neg(V_A \le V_B) \land \neg(V_B \le V_A)
\end{align}
where $V_A \parallel V_B$ designates concurrent, uncoordinated mutations.
\end{definition}

\subsection{Remote Mutation Ingestion}
When GossipSub delivers a remote transaction envelope $\mathcal{E} = \langle \tau_{\text{id}}, \text{type}, n_{\text{sender}}, t, V_{\text{remote}}, \mathcal{O} \rangle$ to peer $n_i$, we process it in three steps:
\begin{enumerate}
    \item \textbf{Idempotency Lookup:} The peer checks its local \texttt{\_mesh\_log} for the UUID $\tau_{\text{id}}$. If we have seen it before, we drop the message immediately.
    \item \textbf{Deterministic Validation:} We run the mutation $\mathcal{O}$ through our standard schema validator against the current local state $\mathcal{D}_i$. If the constraints fail during replay, we reject the write and log a conflict.
    \item \textbf{State Application:} If it passes, we execute the parameterized SQL, append the entry to the \texttt{\_mesh\_log}, and merge the remote vector clock with our local clock component-wise:
\end{enumerate}

\begin{equation}
V_i \leftarrow V_i \sqcup V_{\text{remote}} = \left\langle \max(V_i(n_k), V_{\text{remote}}(n_k)) \right\rangle_{k=1}^K
\end{equation}

\subsection{Convergence Under Validated Replay}

\begin{proposition}[State Convergence Under Validated Replay]
\label{prop:validated-convergence}
Let $D_i$ and $D_j$ denote the database states of peers $n_i$ and
$n_j$. Assume that:
\begin{enumerate}
    \item both peers begin from an identical initial state $D_0$;
    \item both peers successfully apply the same transaction set
    $T = \{\tau_1,\tau_2,\ldots,\tau_m\}$;
    \item every transaction in $T$ is applied at most once, enforced by
    the transaction identifier constraint in \texttt{\_mesh\_log};
    \item validation outcomes are identical across the two peers for
    all transactions in $T$.
\end{enumerate}
Then the resulting database states are identical:
\[
D_i = D_j.
\]
\end{proposition}

\begin{proof}
Under the stated assumptions, both peers begin from the same state and
apply the same deterministic parameterized database operations exactly
once. Duplicate transaction application is prevented by the unique
transaction identifier stored in \texttt{\_mesh\_log}. Therefore,
deterministic replay of the same transaction sequence yields identical
database states.
\end{proof}

\paragraph{Scope of the result}
This proposition is strictly conditional. It proves that validated replay converges identically, but it does \textit{not} guarantee Strong Eventual Consistency for all possible concurrent writes. Two uncoordinated mutations might each pass validation locally on isolated peers, only to conflict when replayed against each other later. When this happens, our implementation rejects the conflicting remote write, causing the replicas to temporarily diverge until an administrator or application-level policy resolves the collision.

\subsection{Conflict Handling and Consistency Limitations}
\label{sec:conflict}
To understand the limits of this design, consider a scenario where peer $n_A$ and peer $n_B$ are separated by a LAN partition:
\begin{enumerate}
    \item While partitioned, peer $n_A$ executes:
    $\text{INSERT}(\text{items}, \{\text{sku: ``SKU-100''}, \text{price: 50}, \dots\})$.
    Validation passes locally; transaction $\tau_A$ is committed to $\mathcal{D}_A$.
    \item Concurrently, peer $n_B$ executes:
    $\text{INSERT}(\text{items}, \{\text{sku: ``SKU-100''}, \text{price: 75}, \dots\})$.
    Validation passes locally; transaction $\tau_B$ is committed to $\mathcal{D}_B$.
    \item Here, $V_A \parallel V_B$. Upon network healing, GossipSub delivers $\tau_B$ to $n_A$ and $\tau_A$ to $n_B$.
    \item When $n_A$ runs $\tau_B$ through its schema validator, the uniqueness check on \texttt{items.sku} fails because \texttt{``SKU-100''} is already in its SQLite file. Consequently, $n_A$ rejects $\tau_B$.
    \item Symmetrically, $n_B$ rejects $\tau_A$ for the same reason.
\end{enumerate}

As a result, peer $n_A$ maintains the price at \$50 while peer $n_B$ holds the price at \$75. Because we lack a Last-Writer-Wins (LWW) resolver or a specialized CRDT merge strategy for relational keys, the two databases diverge on that specific record. Building a robust CRDT merge algebra that natively respects multi-table referential constraints is a complex problem that we leave for future research.

\subsection{Partition Reconciliation Protocol}

When a node powers back on or reconnects to the network, it needs to recover missed transactions. It starts by broadcasting its current vector clock on the \texttt{mesh:sync} topic. Any active peer that receives this request reads the clock, scans its local \texttt{\_mesh\_log}, and gathers all transactions possessing origin counters that exceed the reconnecting peer's known state.

The active peer bundles these missing transactions into a synchronization response. As the reconnecting peer receives the delta, it feeds each transaction back through the exact same remote-ingestion pipeline used during live gossip: idempotency checks, deterministic schema validation, SQLite execution, and vector clock merging.

It is important to note that this is a simple origin-counter log catch-up mechanism, not a comprehensive state-reconciliation algorithm. As demonstrated in Section~\ref{sec:conflict}, transactions that were committed during a network partition might still violate local invariants during replay, meaning that our catch-up protocol alone cannot prevent concurrent conflict divergence.

\begin{algorithm}[t]
\caption{Partition Synchronization and Catch-Up}
\label{alg:partition-sync}
\begin{algorithmic}[1]
\Require Reconnecting peer $n_{rec}$ with clock $V_{rec}$
\Require Online peer $n_{local}$ with ledger $L_{local}$
\State Publish $\mathrm{SYNC\ REQUEST}(n_{rec},V_{rec})$
       on \texttt{mesh:sync}
\State $\Delta \gets \emptyset$
\ForAll{$e \in L_{local}$}
    \State Parse vector clock $V_e$ from $e$
    \State $n_{src} \gets e.\mathrm{peer\_id}$
    \If{$V_e(n_{src}) > V_{rec}(n_{src})$}
        \State $\Delta \gets \Delta \cup \{e\}$
    \EndIf
\EndFor
\State Send $\mathrm{SYNC\ RESPONSE}(n_{rec},\Delta)$
\ForAll{$e \in \Delta$}
    \State Apply $e$ using
           $\mathrm{applyRemoteTransaction}(e)$
\EndFor
\end{algorithmic}
\end{algorithm}

\subsection{Relational Normalization Justification}

We designed the schema structure in Third Normal Form (3NF). In the \texttt{items} table, all non-key attributes depend strictly on the \texttt{id} primary key. We map categorical and supplier data into distinct \texttt{categories} and \texttt{suppliers} tables, utilizing the \texttt{item\_suppliers} associative relation for the many-to-many link. We enforce this decomposition structurally to prevent update anomalies that typically plague denormalized key-value systems.

It is important to clarify that our runtime schema validator does not dynamically prove that incoming data obeys 3NF. The validator's sole job is to execute concrete constraint checks---like ensuring a string fits a datatype, or a foreign key resolves to an existing parent row. We consider normalization a fundamental property of the schema design, whereas the runtime validator merely enforces the operational guardrails dictated by that design.

\subsection{Advisory AI Normalization Audits}
Because schema design can degrade as application requirements evolve, we built an asynchronous background audit agent. This agent periodically reads the DDL schema and a sample of recent \texttt{\_mesh\_log} transactions, asking the LLM if it detects any emerging transitive anomalies or optimization opportunities. We enforce a strict read-only boundary here: the LLM only generates advisory warnings and cannot execute \texttt{ALTER TABLE} statements or block live writes.

\section{Security and Threat Model}
\label{sec:security}

\subsection{Transport Cryptography and Channel Security}
For wire-level security, we rely entirely on the Noise Protocol Framework built into \texttt{@chainsafe/libp2p-noise}. By executing an authenticated Diffie-Hellman key exchange during peer discovery, Noise encrypts all GossipSub traffic. This shields our local mesh from passive packet sniffers and basic man-in-the-middle tampering.

\subsection{Structural Injection Resistance}
We intentionally avoid executing raw SQL strings generated by the LLM. By forcing the language model to return JSON tool calls in the $\mathcal{M}_{\text{tool}}$ format, we substantially reduce the SQL-injection attack surface. We convert those structured operations directly into SQLite parameterized prepared statements, completely bypassing string-concatenation flaws.

\subsection{Threat Model Boundaries and Limitations}
We engineered this prototype for a \textbf{trusted-peer environment}. It is not Byzantine Fault Tolerant (BFT):
\begin{itemize}
    \item \textbf{Absence of Transaction Signatures:} We do not currently sign GossipSub message envelopes with asymmetric keys (like Ed25519). If an attacker breaches the LAN, they could forge transactions using another node's \texttt{peer\_id}.
    \item \textbf{Semantic Sybil / Poisoning Attacks:} If an authorized peer runs modified client software, it can flood the mesh with operations that pass schema validation but destroy data (like issuing valid \texttt{DELETE} commands for every inventory item). Our deterministic validator enforces relational structure, not business-level authorization.
\end{itemize}

\section{Discussion}
\label{sec:discussion}

\subsection{Architectural Trade-offs: Masterless Decentralization}

By abandoning the cloud coordinator, we built a system where nodes never block on external locks when processing local writes. While this architecture thrives in unstable edge networks, we consciously sacrificed global linearizability. Because the SQLite instances operate independently, we cannot provide distributed ACID guarantees for transactions spanning multiple peers. If a deployment strictly requires synchronized, cross-node atomic commits, our current peer-to-peer design is not sufficient.

\subsection{Execution Decoupling and Latency Isolation}

Isolating the inference latency of the language model was a critical design choice. If we placed the LLM on the synchronous write path, standard API traffic would stall behind GPU token generation. By routing unstructured prompts to a decoupled planner while sending structured JSON directly into the schema validator, we ensured the database always runs at the speed of SQLite and the local disk. Even if the local Ollama instance crashes, the node continues executing the fast-path gossip without interruption.

\subsection{Deterministic and Probabilistic Components}

Language models are inherently probabilistic; they guess the next best token. Relational databases are structurally deterministic; a foreign key either exists or it does not. We resolved this tension by explicitly stripping the LLM of execution authority. The model is allowed to interpret intent and propose an operation, but the JavaScript runtime validator makes the final, deterministic decision about whether that operation touches the disk.

% XII. LIMITATIONS
% =========================================================================
\section{Limitations}
\label{sec:limitations}

\begin{enumerate}
    \item \textbf{Independent Storage Scope:} SQLite operates on local disk files. Distributed cross-peer relational joins and distributed aggregations across the mesh are not natively supported.
    \item \textbf{Absence of Distributed ACID Transactions:} Multi-statement transactions spanning multiple peers are not coordinated atomically across the network.
    \item \textbf{Concurrent Conflict Divergence:} When concurrent uncoordinated writes violate unique constraints or foreign keys, conflicting remote transactions are rejected locally, leading to state divergence until manual reconciliation.
    \item \textbf{Informal CRDT Semantics:} Full relational state convergence across arbitrary concurrent mutations is not formally proven to constitute a Conflict-Free Replicated Data Type.
    \item \textbf{Vector Clock Scalability:} In dense peer swarms ($K > 10^3$), vector clock arrays in message envelopes scale linearly with peer count, increasing wire overhead.
    \item \textbf{LAN Operational Boundary:} Peer discovery currently relies on mDNS, confining automated discovery to single broadcast subnets unless explicit relay bootstrap nodes are provisioned.
    \item \textbf{Absence of Cryptographic Envelope Signing:} Envelopes lack digital signatures, assuming a trusted local peer environment.
\end{enumerate}

% XIII. CONCLUSION AND FUTURE WORK
% =========================================================================
\section{Conclusion and Future Work}
\label{sec:conclusion}

We built Agentic Mesh to prove that edge networks can maintain relational database integrity without relying on a central cloud coordinator. By networking independent SQLite databases over a libp2p GossipSub mesh and using vector clocks for causal tracking, we demonstrated a functional, zero-cloud architecture that survives network partitions.

The most significant engineering outcome of this prototype is our bifurcated execution pipeline. We successfully integrated a local Gemma LLM for natural-language intent planning without sacrificing the low latency of standard structured writes. By constraining the LLM to output bounded tool operations and enforcing a deterministic validation layer prior to SQLite execution, we protected the local schema against defined constraint violations, though semantic hallucinations may still produce valid but unintended state mutations.

However, the system is not finished. Our causal replication protocol handles partition catch-up and duplicate detection, but it does not achieve Strong Eventual Consistency. When uncoordinated concurrent writes violate unique relational constraints, the receiving nodes reject the conflicting data, leading to localized replica divergence. We also have not implemented asymmetric cryptographic signatures to prevent internal spoofing.

Our next steps include executing the large-scale benchmark suite described in our evaluation methodology. We also plan to investigate CRDT merge semantics capable of preserving relational invariants, implement Ed25519 transaction signing, and develop deterministic reconciliation strategies for concurrent schema conflicts.
